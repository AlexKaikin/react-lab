# Архитектура (FSD)

Проект построен по методологии **Feature-Sliced Design (FSD)**. Код организован в слои, каждый из которых решает свою задачу и знает только о нижележащих слоях.

## Слои (Layers)

| Слой       | Назначение                                     | Примеры из проекта             |
| ---------- | ---------------------------------------------- | ------------------------------ |
| `app`      | Next.js App Router: страницы, лэйауты, роутинг | `layout.tsx`, `page.tsx`       |
| `pages`    | Страницы приложения, композиция виджетов       | `home`                         |
| `widgets`  | Композиционные блоки из фич и сущностей        | `header`                       |
| `features` | Пользовательские сценарии (взаимодействия)     | `theme`                        |
| `entities` | Бизнес-сущности                                | _пока отсутствует_             |
| `shared`   | Переиспользуемый код: UI-кит, утилиты, типы    | `button`, `icon`, `classNames` |

## Правила зависимостей

Слои импортируют код только из слоёв **ниже** по иерархии. Обратные и горизонтальные импорты между слоями одного уровня запрещены.

## Сегменты (Segments)

Каждый слайс внутри слоя делится на сегменты:

| Сегмент  | Назначение                        | Примеры                                    |
| -------- | --------------------------------- | ------------------------------------------ |
| `ui`     | React-компоненты и отрисовка      | `header.tsx`, `theme-provider.tsx`         |
| `model`  | Состояние, сторы, типы, константы | `use-theme.ts`, `types.ts`, `constants.ts` |
| `lib`    | Вспомогательные функции и утилиты | `classNames.ts`                            |
| `api`    | Запросы к API                     | _пока отсутствует_                         |
| `config` | Конфигурация слайса               | _пока отсутствует_                         |

## Публичное API (index.ts)

Каждый слайс экспортирует содержимое через `index.ts`. Внутренняя реализация скрыта.

# Принципы написания кода

## Вёрстка

- Семантические теги
- Доступность (a11y)
- Валидность W3C
- **Локализация a11y- и пользовательских строк**: любой текст, видимый пользователю или зачитываемый скринридером —
  включая `aria-label`, `aria-description`, `alt`, `title`, `placeholder`, а не только children/текст между тегами —
  должен браться из `next-intl` (`useTranslations`/`getTranslations`), а не быть захардкожен, если в проекте
  подключена мультиязычность.
- **Шкала отступов**: все `gap`/`padding`/`margin` — кратны 4px (`4/8/16/24/32...`, т.е. Tailwind `1/2/4/6/8`).
  Не смешивать с произвольными значениями вроде `gap-3`/`p-7`. Внутри одного компонента отступы должны расти по
  этой шкале от меньшего (плотная связь, напр. поле формы ↔ его ошибка) к большему (границы блоков/секций).
- **Разделяй gap «внутри элемента» и gap «между элементами»**: если у элемента есть подпись/ошибка/подсказка —
  их отступ друг от друга должен быть меньше и фиксирован отдельным контейнером, а не общим `gap` родительского
  списка. Пример: `FormInput` оборачивает `Input`+`FieldError` в свой `flex flex-col gap-2`, а форма снаружи
  задаёт `gap-4` только между полями (`src/shared/ui/form/form-input/ui/form-input.tsx`).
- **Единая высота интерактивных элементов в одном ряду**: инпуты и кнопки одного контекста (например, форма)
  должны иметь одинаковую высоту (`h-12` у `Input` и `size="medium"` у `Button`), иначе ряд выглядит неаккуратно.
- **Фокус на инпутах**: явно менять и `border-color`, и добавлять `ring` (не только ring) — так фокус читается
  однозначно, а не сливается с обычной рамкой.
- **Визуальная идентичность нового компонента — до сборки**: прежде чем вёрстать новый интерактивный элемент из
  готовых примитивов (`Button`, `Input`...), определи его собственный визуальный язык: на что он похож по роли —
  на поле ввода (`border-secondary`/`bg-primary/20`/`backdrop-blur-sm`, как `Input`), на действие (как `Button`)
  или на самостоятельный виджет с собственной группировкой (трек+таблетка у переключателя, а не две рядом стоящие
  `Button`).
- **Составные/композитные элементы управления** (переключатели/табы, сегментированные контролы, кастомные селекты)
  не сдавать первым проходом как голую семантическую разметку без визуального группирования — стилизация как
  единого виджета — часть ТЗ, а не отдельная итерация после фидбека.
- **Три размера** (`small`/`medium`/`large`) — единая шкала высот для всех интерактивных элементов (`h-10`/`h-12`/
  `h-14`, как у `Button`) — новый компонент должен её повторять, а не вводить свои значения.

## Скрипты

- Строгая типизация (TypeScript)
- Производительность: мемоизация, динамический импорт, Server/Client разделение
- Безопасность: XSS, CSRF, валидация на границах
- Принципы: DRY / SOLID / KISS
- Состояние: приоритет Server State, минимум Client State
- Оптимизация рендера: изображения, шрифты, CLS
- **Ленивая загрузка модалок**: компоненты, передаваемые в `openModal`, должны импортироваться через `next/dynamic` или `React.lazy`, чтобы не увеличивать бандл страницы. Исключение — если модалка гарантированно весит <1KB и будет вызвана сразу.
- **`getTranslations` только с явным `locale`**: в Server Components вызывать `getTranslations({ locale, namespace })`, никогда `getTranslations(namespace)` без локали. Голый вызов без явного `locale` во вложенном Server Component тихо ломает статическую генерацию (`generateStaticParams`/SSG превращается в `ƒ`), даже если `setRequestLocale` уже был вызван в родительском layout — проверено эмпирически на этом проекте.

## Локализация данных (БД)

- Многоязычный контент моделируется как база + перевод: базовая модель хранит дефолтную локаль (`defaultLocale`) прямо в своих полях, соседняя модель `<Entity>Translation` — только остальные языки, с обязательным `locale` и `@@unique([entityId, locale])` (защита от дублей перевода).
- Если перевода для запрошенной локали нет — 404, а не молчаливый откат на дефолтный язык: подмена языка вводит в заблуждение и создаёт дублирующийся контент для поисковиков.
- Пример: `Post`/`PostTranslation`, `PostCategory`/`PostCategoryTranslation` (`prisma/schema/post.prisma`, `post-category.prisma`).

## Паттерны проектирования

- Применяй паттерны только когда они решают конкретную проблему, не ради структуры
- Приоритет: композиция > наследование
- Избегай: God Object, преждевременной абстракции, магических значений
- Используй: `Factory` для API-клиентов, `Strategy` для валидации, `Observer` для событий, `Compound Components` для гибких UI, `Repository` для данных
